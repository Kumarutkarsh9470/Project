How to use this guide

Every topic here matches one topic in the deck, in the same order. Each one follows the same path:

  1. What goes wrong, told as an exact timeline of two threads.
  2. Why it goes wrong.
  3. The idea that fixes it, and what it costs.
  4. What you'll see when you run the version's programs, and why.

Timelines read top to bottom. Each thread gets its own column, so you can see exactly where they interleave:

Thread 1                         Thread 2

step A
                                 step B      ← happens in between
step C

Two practical rules before you start.

Only study the main files. In master/, each version's real work is in queue.hpp (later pool.hpp and friends) and the tiny examples. The helpers in common/ (test macros, a stopwatch, a thread owner) are tools. You don't need to read them.

Predict before you run. Write your guess down. A wrong guess you can explain is worth more than a right one you can't.

Part 1 · Build the queue

We start with an ordinary std::queue and break it, one requirement at a time, until it is a thread-safe queue that many producers and consumers can share and shut down cleanly.

v0 · Ordinary queueWhat does a second thread actually buy us?

Our first program does one thing at a time. A producer fills the queue, then a consumer drains it.

time →
[ produce produce produce ][ consume consume consume ]

It's tempting to think: "Put them on two threads and it'll be twice as fast." Sometimes that's true. Often it isn't. We need to know which one we're getting.

Look at what a CPU core actually does with two threads.

One core, two threads

core 0:  T1 T1 T2 T1 T2 T2 T1      ← the OS switches between them

Two cores, two threads

core 0:  T1 T1 T1 T1 T1 T1 T1
core 1:  T2 T2 T2 T2 T2 T2 T2      ← really at the same time

On one core, the two threads only take turns. That is concurrency: two tasks in progress. On two cores, they run at the same instant. That is parallelism, and it needs hardware.

So when does concurrency alone help? When a task spends its time waiting. While T1 waits for a disk or a network reply, the core is free, and T2 can use it.

Two tasks that each sleep 2 s

one thread:   [ sleep 2s ][ sleep 2s ]          = 4 s
two threads:  [ sleep 2s ]
              [ sleep 2s ]                      = 2 s

Neither task got faster. The waiting overlapped.

Threads overlap waiting. Only more cores speed up computing.

What you'll seetiny prints sequential 4.0 s, two threads 2.0 s. The tests time a million push + pop pairs, about 60 ns each. Write that number down: every later version is compared to it.

v1 · Multiple threadsWho owns a thread?

Now the producer and consumer get their own threads. The first surprise comes before any data is shared.

void work() { /* ... */ }

int main() {
    std::thread t(work);
}   // t is destroyed here

This program crashes. Not sometimes. Every time. Why?

A std::thread object is a handle that owns a running OS thread. When the handle is destroyed, C++ asks: what should happen to the thread it owns? There are only two sensible answers, and you must pick one first.

std::thread object ──owns──▶ OS thread

before the object dies, choose:
   join()    wait here until the thread finishes
   detach()  let it run on, with no owner

destroyed while still joinable → std::terminate

C++ refuses to guess. Guessing "join" could freeze your program; guessing "detach" could leave a thread using memory that's about to vanish. So it terminates.

The second surprise: arguments are copied into the new thread. If you pass your queue, the thread gets its own copy and fills that instead. To share the real one, wrap it: std::ref(queue).

The fix for forgetting to join is the same fix C++ uses everywhere: give the job to a destructor. A small class, ThreadGroup, holds threads and joins them all when it goes out of scope. Even if an exception flies past, the destructor still runs.

Every thread needs exactly one owner that joins it. Let a destructor be that owner.

What you'll seetiny terminate aborts. next_bug, with 4 producers pushing 100,000 items each into one plain std::queue, segfaults or hangs. Four threads are now inside push() at the same time. That's v2.

v2 · Mutex protectedWhere did the updates go?

Four producers crashed the queue. To see why, shrink the problem to one line of code that two threads both run a million times:

int counter = 0;
void increment() { for (int i = 0; i < 1'000'000; ++i) ++counter; }

Two threads, a million each. The answer should be 2,000,000. Run it and you get 1,556,397. Then 1,114,575. Never the same twice.

++counter looks like one step. It's three: read the value, add one, write it back. Now watch two threads interleave them:

Thread 1                         Thread 2

read counter → 0
                                 read counter → 0
add 1 → 1
                                 add 1 → 1
write 1
                                 write 1

counter is 1. Two increments happened. One was lost.

Nothing crashed. One update simply vanished. Inside std::queue::push the same thing happens to its internal pointers, and a lost pointer update corrupts memory. That was v1's crash.

This is a data race: two threads touch the same memory, at least one writes, and nothing orders them. In C++ that's undefined behaviour. Anything may happen.

The fix is to make the read-add-write happen one thread at a time. A std::mutex is a lock only one thread can hold:

Thread 1                         Thread 2

lock m
read 0, add, write 1
                                 lock m   ← must wait
unlock m
                                 (gets m) read 1, add, write 2
                                 unlock m

One rule makes it work: every access to the shared data goes through the same mutex. The mutex protects data, not code.

A data race is unsynchronized access with at least one write. A mutex turns it into taking turns.

What you'll seeThe tiny counter prints a different wrong number every run. The tests pass now, but push gets slower with 4 threads (about 140 ns vs 44 ns): they queue up for one lock. next_bug hangs: pop() threw while holding the mutex, and nobody unlocked it. That's v3.

v3 · RAII lockingThe lock that never unlocks

v2 locks by hand:

int pop() {
    m.lock();
    if (q.empty()) throw std::runtime_error("empty");   // leaves here…
    int v = q.front(); q.pop();
    m.unlock();                                          // …so this never runs
    return v;
}

Follow one consumer that arrives too early:

Consumer                         Producer

lock m
queue empty → throw
   ↓
exception leaves pop()
m is still locked
                                 push(42): lock m … waits forever
everyone else: waits forever

One exception, one skipped line, and the whole program freezes.

We've seen this shape before in v1: "something must happen on every way out of a scope." C++'s answer is a destructor. When an exception unwinds the stack, the destructor of every local object still runs.

{
    std::lock_guard<std::mutex> lock(m);   ← constructor: lock
    ... return early, throw, anything ...
}                                          ← destructor: unlock, always

This is RAII: tie a resource to an object's lifetime. You stop calling unlock() yourself, so you can't forget it.

One trap: std::lock_guard<std::mutex>(m); with no variable name creates a temporary that unlocks at the semicolon. Always name it.

Never unlock by hand. Let a destructor release the lock on every path out.

What you'll seetiny_raii prints try_lock after the exception: 0: the mutex is still held. With lock_guard, it's free.

v3 · Interface racesEvery call locks. Why does it still fail?

Consumers now play it safe. They check before they take:

if (!q.empty())
    x = q.pop();

empty() locks. pop() locks. Every single call is protected. And yet, with two consumers and one item left, pop() still throws "empty". Look at the gap:

Consumer A                       Consumer B

lock, empty()? → no, unlock
                                 lock, empty()? → no, unlock
lock, pop() → 42, unlock
                                 lock, pop() → queue is empty!

Each call was safe. The pair of calls wasn't. Between A's check and A's act, B slipped in.

This is a race condition without a data race. No memory was touched unsafely, so tools like ThreadSanitizer stay silent. The bug is in the shape of the interface: it makes the caller do "check, then act" across two separate locks.

The fix is to offer the whole operation as one call, under one lock:

bool try_pop(int& out);   // lock, check, take, unlock: one step

It never throws; it returns false when there's nothing to take. And empty() now only means "was empty a moment ago", so nobody should act on it.

A check and the action it guards must happen under one lock. Design the interface so they can't be split.

What you'll seetiny_interface: top() hit an empty stack in 186 of 200 rounds. next_bug: an idle consumer looping on try_pop checks an empty queue about 10 million times a second, burning a whole core. That's v4.

v4 · condition_variableWaiting without spinning

try_pop returned false. The consumer has nothing to do. What now?

The obvious options are all bad. Spinning on try_pop burns a core. Sleeping inside the locked queue freezes the producer out. So let's try the next idea: unlock, nap, try again.

if (q.empty()) {
    m.unlock();
    sleep(1);
    m.lock();
}
int value = q.front();

Watch the dangerous timing:

Consumer                         Producer

lock mutex
q.empty() → YES
unlock mutex
                                 lock mutex
                                 push(42)
                                 unlock
sleep(1)          ← the item is already there
wake up
lock, pop(42)

It works, but the consumer slept a full second for an item that was already waiting. So let's replace the sleep with a notification: the producer says "item ready", and the consumer wakes. Now look at the gap between unlocking and starting to wait:

Consumer                         Producer

"queue empty"
unlock
     ← scheduling gap →
                                 push item
                                 notify      ← nobody is waiting yet
start waiting
   😴 forever

The notification happened before the consumer began waiting, so it was lost. An item sits in the queue, and the consumer sleeps forever. This is the lost wake-up.

The real problem is the gap between unlocking and going to sleep. We need one operation that releases the lock and starts waiting as a single step. That's std::condition_variable::wait():

lock
check condition
if false:
    release lock + sleep        ← one step: no gap
someone changes the condition, then notifies
wake up
re-take the lock
check the condition again

That last line matters. A woken thread can't assume the item is there: another consumer may have taken it first, and threads can even wake up for no reason (a spurious wake-up). So the mental model is a loop:

while (!condition) sleep;      // not: if (!condition) sleep;

and the code passes the condition as a predicate, which does exactly that loop for you:

std::unique_lock<std::mutex> lock(m);
cv.wait(lock, [&] { return !q.empty(); });

Why unique_lock and not lock_guard? Because wait() must unlock the mutex while sleeping and lock it again before returning. lock_guard can't be unlocked.

Our queue has grown:

std::queue                         (v0)
std::queue + std::mutex            (v2: safe access)
std::queue + std::mutex
           + condition_variable    (v4: efficient waiting)

wait() releases the lock and sleeps in one step, and always re-checks the condition when it wakes.

What you'll seetiny spin burns 100% CPU, nap reacts late, locked freezes. next_bug hangs: it waits without a predicate, the producer notified first, and the wake-up was lost.

v5 · Many producers and consumersProving it under load

One producer and one consumer work. Real systems have many of each. One run that prints the right number proves almost nothing, because concurrency bugs depend on timing. We need tests a bug can't hide from.

So we build a test matrix: 1×1, 4×1, 1×4, 4×4, tiny and huge item counts, slow producers, slow consumers. Each run checks:

  • the count matches: nothing lost;
  • the sum matches: a duplicate and a loss can't cancel out;
  • no hang, and idle threads near 0% CPU.

Why did 1,000 items per producer hide v1's crash? Each thread finished before the next one even started. They never overlapped. Use 100,000.

The matrix also shows a cost. Four threads, one mutex:

T1 ██ lock ██ ......... ██ lock ██
T2 ... waiting ... ██ lock ██ .....
T3 ....... waiting ....... ██ lock ██
T4 .......... waiting ..........

That's contention: threads lining up for one lock. Passing the lock between cores costs more than the tiny push itself. The cure is to share less: do work locally, and touch the shared thing rarely.

Concurrent code is proven by stress tests across workloads, never by one run.

What you'll seetiny_contention: locking per item 413 ms, locking once 3 ms, same answer. In the tests, push_all batches beat single pushes about 4×.

v5 · DeadlockTwo queues, two locks, frozen

With many consumers, one queue can pile up while another runs dry, so we add move_all_to(other). It needs both queues' locks. Two threads move in opposite directions:

Thread 1: q1.move_all_to(q2)     Thread 2: q2.move_all_to(q1)

lock q1.m
                                 lock q2.m
want q2.m … wait
                                 want q1.m … wait

both wait forever

Draw who waits for whom:

T1 holds q1.m ──waits for──▶ q2.m
T2 holds q2.m ──waits for──▶ q1.m
          ↑___________________________|   a cycle

A cycle in this wait-for graph is a deadlock. Break the cycle and it can't happen. Two ways:

  • Take both locks together: std::scoped_lock lock(m, other.m); uses an algorithm that never deadlocks.
  • Always lock in one global order, for example by address.

Check this == &other first: locking the same mutex twice is undefined behaviour.

A second trap: push_all locks the mutex and then calls the public push(), which tries to lock it again. One thread now waits for itself. The clean fix: public functions lock, private helpers (push_locked) assume the lock is held. Reaching for recursive_mutex usually means the lock boundaries don't match the operations.

Take several locks together or in one fixed order. Never lock the same mutex twice.

What you'll seetiny_deadlock and next_bug hang. That's the point: let them run 10 seconds, then stop them.

v6 · Graceful shutdownThe producers are done. The program never exits.

Consumers no longer know how many items to expect, so they loop on wait_and_pop() forever. When the producers finish:

Producers                        Consumers

push last item
return
                                 pop last item
                                 wait_and_pop() … sleep
main: join consumers … waits
                                 … asleep forever

Nobody can say "no more items are coming". The queue needs states:

RUNNING    push ok · pop waits
   ↓ shutdown()
CLOSED     push rejected · every waiter woken
   ↓ queue drains
DRAINED    wait_and_pop() returns "nothing"
   ↓
consumers return · threads are joined

shutdown() sets closed = true under the lock (otherwise it's a data race, and the change can slip into a consumer's check-then-sleep gap, exactly like v4), then calls notify_all(). Why all? With notify_one:

Consumer A          Consumer B          main

sleeping            sleeping            shutdown(): notify_one
wakes, sees closed
returns
                    still asleep … forever

Every waiter must hear the news. And how does a woken consumer say "nothing"? No int value can mean that, so wait_and_pop() returns std::optional<int>: a value, or empty when closed and drained.

Shutdown is a protocol: change the state under the lock, wake everyone, let each waiter see it.

What you'll seetiny hangs with notify_one: one waiter wakes, the other sleeps on. Change one word to notify_all and it exits.

v7 · Generic queue<T>A queue of anything, including things you can't copy

Soon we'll queue tasks, not ints. Some values can't be copied at all (std::unique_ptr), so the queue becomes a template that moves values in and out.

There's a subtle trap in returning a value from pop():

T pop() {
    T v = std::move(q.front());
    q.pop();                     ← item removed from the queue
    return v;
}
caller:  x = queue.pop();        ← if this assignment throws,
                                   the item is gone for good

That's why std::queue::pop() returns void. Our wait_and_pop() returns std::optional<T> built by moving, and moves of standard types don't throw.

Push takes T by value and moves it in, so it works for both copyable and move-only types. The queue itself can't be copied: a mutex can't be copied, and copying a queue other threads are using has no sensible meaning.

A generic concurrent container moves its values and never loses one when something throws.

What you'll seetiny prints moved out: 42. ThreadSafeQueue<std::unique_ptr<int>> now compiles. This is the end of Part 1: run every earlier test against v7 before going on.

Part 2 · Grow it into a thread pool

Part 1 asked: how do threads share a queue safely? Part 2 asks a different question: how does a caller get work done on another thread, and get the answer back?

v8 · Task queueWhat if the queue carried work?

Instead of ints, we push functions: "run this". One worker thread pops them and runs them.

main thread                          worker thread

push(task) ──▶ [ task queue ] ──▶ pop, task()

Two new questions appear immediately.

Where does an exception go?

main                             worker

try {
  push(task_that_throws)
} catch (...) { }  ← already done
                                 task() throws
                                 unwinds the WORKER's stack
                                 leaves the thread function
                                 → std::terminate

An exception only travels up the stack of the thread that threw it. main's try is on a different stack, and it finished long ago. So the worker must catch everything, or one bad task kills the program.

What does the task point at?

A task that captures a local by reference runs later, maybe after that function returned and its locals were destroyed. Queued tasks should capture by value.

Catching in the worker keeps the program alive. But look at what's still missing: the caller never learns its task failed, and never gets a result.

An exception can't cross threads on its own. Catch it where it happens and carry it back.

What you'll seetiny terminate aborts. next_bug prints The 42 is gone, and main can't tell a task failed. That's what v9 and v10 fix.

v9 · Thread poolOne worker isn't enough. How many?

N workers share one task queue. That's a thread pool:

submit(task) ──▶ [ task queue ] ──▶ worker 1
                                ──▶ worker 2
                                ──▶ worker N

The order of destruction matters

class ThreadPool {
    ThreadSafeQueue<Task> tasks;    // built first, destroyed last
    ThreadGroup workers;            // built second, destroyed first
};

Members are destroyed in reverse order of declaration. The destructor first calls tasks.shutdown() so sleeping workers wake up, then the workers are joined, and only then does the queue disappear. Swap the two members and the queue is destroyed while workers still use it.

How many workers?

It depends on what the tasks do, exactly like v0:

64 tasks that wait (sleep, network):   more threads → faster
64 tasks that compute:                 speedup stops at the core count;
                                       more threads only add switching

For computing, about one worker per core. For waiting, many more.

What you'll seeSleepy tasks finish faster with more threads; busy tasks stop improving at the core count. Destroying the pool with 1,000 queued tasks runs all of them first.

v9 · Real workloadsThree day-one problems

A realistic job downloads something, computes on it, and stores the result in a shared vector. The first version locks the whole job:

lock around the whole task
w1 ██████████
w2           ██████████
w3                     ██████████        8 workers, as slow as 1

lock around the shared line only
w1 ████████▌
w2 ████████▌
w3 ████████▌                             ▌ = the one locked push_back

Only results.push_back(r) touches shared data. Lock just that line. Lock less, and the workers actually run in parallel.

Many readers, rare writers. Every job reads a shared DNS cache; updates are rare. A std::shared_mutex lets many readers in at once (shared_lock) and gives writers exclusive access (unique_lock). Our queue can't use it: every queue operation writes.

Create something once. Many threads call default_pool(). The naive if (!pool) pool = new ThreadPool; is a data race: two threads can both see null and both create a pool. A function-local static (or std::call_once) is guaranteed to initialise exactly once.

Lock the shared touch, not the whole task. Share reads. Initialise once.

What you'll seetiny_granularity: locking everything 3.2 s, locking only push_back 0.4 s. Same 64 results.

v10 · Future-based resultsThe caller wants the answer, or the error

Building "send a result back" by hand needs a value, a ready flag, a mutex, a condition variable and an exception_ptr. Every time. The standard library packages all of it as a one-shot channel:

write end                 shared state                 read end
packaged_task ──set──▶ [ value or exception ] ──▶ future.get()
or promise               + ready flag              waits, then
                         + mutex + cv (hidden)     returns or rethrows

The pool wraps each callable in a std::packaged_task and hands the caller its std::future:

auto f = pool.submit([] { return 6 * 7; });
int x = f.get();        // waits; returns 42, or rethrows the task's exception

One wrinkle: packaged_task is move-only, but std::function requires copyable callables. Storing it in a std::shared_ptr makes the wrapper copyable.

get() is one-shot: it moves the result out. A second call has nothing left to give.

When threads exchange results instead of sharing state, use a future.

What you'll seetiny_future: with launch::deferred, calculate() runs on main's own thread, inside get(). A throwing task is rethrown by get().

v10 · promise and shared_futureNo function to run, or many readers

Sometimes a result doesn't come from a function you can wrap. A network reply arrives in a callback. For that there's std::promise: you hold the write end and call set_value() (or set_exception()) yourself.

who produces the value?
  std::async          the library runs it
  std::packaged_task  you choose where it runs
  std::promise        nobody runs anything: set it by hand

how many readers?
  std::future         one    (like unique_ptr)
  std::shared_future  many   (like shared_ptr)

Eight tasks need one loaded config? Call .share() and give each task its own copy of the shared_future. Copies share the state safely; one object used by many threads would be a data race.

If a promise is destroyed without being set, every reader gets a broken_promise error instead of waiting forever.

One reader: future. Many readers: shared_future, one copy each. No function: promise.

What you'll seetiny_promise: first reader got 42, then second get(): No associated state.

v10 · Timeouts and cancellationA task that never finishes

A task calls fetch(), which sometimes hangs. The caller gives up after a second:

caller                           worker

wait_for(1s) … timeout
"give up"
                                 fetch() … still running
leave the scope
pool destructor: join … waits    fetch() … still running

A timeout only stops waiting. The work goes on. And C++ will never kill a thread for you: it might hold a lock or be halfway through updating shared data.

So cancellation must be cooperative. C++20 gives you a thread-safe "please stop" flag: std::stop_source sets it, and the task checks its std::stop_token between steps and returns early.

Two kinds of timeout: wait_for is relative ("one more second"), wait_until is a deadline shared by several steps.

A timeout limits your waiting. Only the task can stop itself, when asked.

What you'll seetiny_timeout: timed out at 1.0 s, left the scope at 3.0 s. The future from std::async waits for the task in its destructor.

v10 · Tasks waiting on tasksThe pool that freezes with nothing locked

A recursive algorithm splits its work: each task submits half and waits for that half's future. Two workers, two such tasks:

Worker 1                         Worker 2

run outer A
  submit inner A
  inner_A.get() … waits
                                 run outer B
                                   submit inner B
                                   inner_B.get() … waits

queue: [ inner A, inner B ]  ← no free worker to run them

No mutex is held. Everything is waiting. A future.get() is a wait-for edge, just like a lock in v5:

worker 1 → inner A → needs a free worker → workers 1, 2 → …   a cycle

More workers only move the limit: N blocking tasks need more than N workers, and recursion creates them fast.

The fix: while a worker waits, it helps. Instead of sleeping in get(), it pops other queued tasks and runs them, possibly the very task it's waiting for:

while (f.wait_for(0s) != std::future_status::ready) {
    Task t;
    if (tasks.try_pop(t)) t();        // help instead of sleeping
    else std::this_thread::yield();
}
return f.get();

That's wait_helping, and it finally gives v3's try_pop a real job.

A blocking get() inside a pool task is a wait-for edge. Help while you wait.

What you'll seetiny_nested hangs. The recursive psum with wait_helping finishes correctly even on a 1-worker pool.

Part 3 · Faster, and measured

The pool works. Part 3 asks what all that safety costs, and how to pay less: the same queue rebuilt with atomics, with two locks, with no locks, and then measured properly.

v11 · AtomicsCounting without a lock

A dashboard thread wants to read the pool's "submitted" and "completed" counts every 100 ms. Putting them under a mutex works, but now every finished task queues behind the dashboard for that lock. Is a mutex the only way to make ++ safe?

Go back to v2's lost update. The problem was that ++n is three steps another thread can get between:

++n on a plain int:     load → add → store       (3 steps, can interleave)
n.fetch_add(1):         load+add+store           (1 indivisible step)

A std::atomic<int> does the read-modify-write as one hardware operation. Nobody can land in the middle, and nobody ever waits for a lock.

A trap: counter = counter + 1 on an atomic is an atomic load, then a separate atomic store. Two steps again, and updates are lost again. Only single operations are atomic.

The second question: what else does the other thread see?

Atomicity stops lost updates. But often one thread prepares data and then raises a flag:

Writer                           Reader

data = 42;          (plain int)
ready = true;       (atomic)
                                 sees ready == true
                                 reads data → 42?  or 0?

Without more care, the reader can see the flag but not the data: compilers and CPUs may reorder the writes. Memory order controls this:

  • memory_order_relaxed: the operation is atomic, nothing more. Enough for a counter.
  • store(…, release) + load(…, acquire): everything written before the release store is visible after an acquire load that reads it. This is how you publish data.

If unsure, the default (sequentially consistent) is always correct, just slower.

Atomic stops lost updates. Release/acquire decides what else the other thread is allowed to see.

What you'll seetiny_atomic at -O0: no lock ≈ 1,056,548 (wrong), mutex 2,000,000 in about 200 ms, atomic 2,000,000 in about 27 ms. At -O2 the no-lock line may print 2,000,000 because the compiler merged the loop; it's still a bug. next_bug: queue throughput doesn't grow as you add threads. That's v12.

v12 · Two-lock queueProducers and consumers share one lock

A producer only touches the tail of the queue. A consumer only touches the head. Yet with one mutex, each waits for the other. Can we give each end its own lock?

head_m                         tail_m
  ▼                              ▼
[ a ] → [ b ] → [ c ] → [ dummy ]

consumers take from the head
producers fill the dummy at the tail and append a new dummy

The queue becomes a linked list that always ends in an empty dummy node. Because the tail always points at that dummy, head and tail never point at the same real item, and the two locks never guard the same node.

The lost wake-up, again

Consumers wait under head_m, but producers now only hold tail_m. That reopens v4's gap:

Consumer (holds head_m)          Producer (holds only tail_m)

check: no items
                                 append item
                                 notify      ← nobody waiting yet
start waiting
   😴

The fix is one odd-looking line in push(): lock head_m for an instant before notifying. The producer then can't notify in the middle of a consumer's check-then-sleep.

Did it help?

Most people predict yes. Measure it. Two locks remove waiting, but every push now allocates a node and takes two locks. On a 4-core machine at -O2, one mutex moved 6.1 million items a second; the two-lock queue moved 0.9 million.

Splitting a lock trades less waiting for more work per operation. Only a measurement says which wins.

What you'll seeBuild tiny_contention at -O2 (at -O0 it is very slow). next_bug: one producer and one consumer pay 1–4 microseconds per item. Far too slow for a feed. That's v13.

v13 · Lock-free SPSC ringOne producer, one consumer, no locks

A feed handler has exactly one thread reading the network and one thread parsing. Locks, allocation and sleeping each cost more than the message. With exactly one writer per index, we don't need any of them.

slots: [ . | a | b | c | . | . | . | . ]
             ▲           ▲
            head        tail

the consumer owns head   (only it writes head)
the producer owns tail   (only it writes tail)
each only READS the other's index

Walk one item through:

Producer                         Consumer

write slot 5
tail.store(6, release)  ─────▶   tail.load(acquire) == 6
                                 slot 5 is guaranteed visible
                                 read slot 5
                                 head.store(6, release)
sees head == 6  ◀─────────────   (slot 5 may be reused)

That's v11's publish pattern, twice. No lock, no allocation: a fixed array of N slots (N a power of two, so index & (N - 1) wraps cheaply). The API is try_push / try_pop only; the caller decides whether to spin, yield or sleep.

False sharing

Caches move memory in 64-byte lines. If head and tail sit on one line, every write by the producer steals the line from the consumer's core, and back again, though they never touch each other's variable. Putting each on its own line (alignas(64)) stops the ping-pong.

The price of all this: exactly one producer and one consumer. Break the rule and it fails silently.

Lock-free code is only correct under its stated rules. SPSC: one writer per index.

What you'll seetiny_false_sharing: same cache line 1.5 s, separate lines 0.4 s, with nothing shared. next_bug (two producers): expected 2,000,000 items, the consumer got 1,255,101.

v14 · Benchmark harnessWhich queue is fastest? Prove it.

We have three queues and plenty of opinions. So far every number came from one run, at whatever load, as one average. That's an anecdote.

First trap: the compiler.

loop whose result nobody uses   → -O2 deletes it   → "0 ms"
loop whose result is printed    → must run         → 640 ms

A benchmark must use its result, and must be built the way you ship (-O2).

Then measure two different things:

throughput   how many per second, flat out
latency      how long ONE message waits

p50     the typical message
p99     1 in 100 is slower than this
p99.9   1 in 1,000: where the trouble lives

Rules the harness follows: warm up first and discard it (cold caches, page faults); repeat five times and report the median (one noisy run can't move it); measure latency at a steady, paced rate below capacity, or you only time your own backlog.

                   M msg/s     latency at 500k msg/s
queue (1P/1C)      saturated   p50       p99
ThreadSafeQueue      4.8       5.8 µs    0.9 ms
TwoLockQueue         0.8      18.3 µs    3.6 ms
SpscRing           104.8       0.26 µs  0.05 ms

Your machine's numbers will differ. The ranking is what to check, and the reason for it: no locks, no allocation, no sleeping. Even the ring's p99.9 reaches about a millisecond: that's the operating system pausing a thread, which is the Feed Handler's next problem.

One number from one run is an anecdote. Report the median, and read the tail.

What you'll seeBuild bench.cpp at -O2 and compare with the table above.

Where this leaves you

Every tool in this track arrived because the project broke without it: a mutex for the lost update, a destructor for the forgotten unlock, a condition variable for the lost wake-up, a future for the lost result, an atomic for the contended counter, a ring for the slow hand-off. If you can name the bug behind each one, you're ready for the project tracks.
