Part 1 · Build the queue (v0–v7)

v0

What would a second thread buy us?

queue v0

Queue v0 · What concurrency buys

1–2 · Problem

Our program does one thing at a time: produce every item, then consume every item. Producing and consuming could overlap. But overlapping isn't the same as going faster, and we need to know which one we're getting.

In our project: Queue v0 is a plain std::queue<int> wrapper. A producer function fills it, then a consumer function drains it, one after the other on one thread.

2 · Mental model
One core, two threads  (time →)
core 0:  T1 T1 T2 T1 T2 T2 T1   OS switches
                                  between them
Two cores
core 0:  T1 T1 T1 T1 T1 T1 T1
core 1:  T2 T2 T2 T2 T2 T2 T2   truly at once

Concurrency: several tasks in progress. Parallelism: tasks running at the same instant, which needs more than one core.

3–5 · Tiny example

Two tasks, two seconds each. Predict:

  • How long does each version take? Write both numbers down.
  • Did either task itself get faster?

Then break it:

  • Replace the sleep with a CPU loop and run 1, 2, cores and 4× cores threads.
  • Make both threads print 1–1000. Is the order the same every run?
6–7 · Explain + fix

Threads overlap waiting. CPU work needs cores.. Concurrency is structure: tasks in progress together. Parallelism is hardware: tasks running at the same instant.

8 · Project version
  • Nothing is concurrent yet. That's the point: we need a correct, measured baseline before adding threads.
  • pop() on an empty queue is undefined behaviour. We'll have to deal with that once threads arrive.

Must pass:

  • producer(q, 1,000,000) then consumer(q, 1,000,000): size() is 0
  • Time it at -O2. Write down ns per push + pop
9 · Exercises
  1. Measure v0: 1,000,000 pushes and pops at -O2. Record ns per operation. Every later version is compared to this number.
  2. Run two threads that each print 1–1000. Record how many different orders you get in 20 runs.
  3. Plot burn() speedup for 1 to 2× cores threads. Where does the curve bend, and why?
10 · Checkpoint answers
  1. Concurrency vs parallelism, one sentence each.
    Concurrency: more than one task in progress (structure). Parallelism: running at the same instant (needs cores).
  2. Can two threads make a program faster on one core? When?
    Yes, when the work involves waiting (I/O, network, sleeps, user input). Not for pure CPU work.
  3. Who decides which thread runs next?
    The OS scheduler. Our code can only constrain it with synchronization.
  4. Why is hardware_concurrency() only a hint?
    It may return 0 (unknown), and logical cores (hyper-threads) aren't full cores.
v1

What does a std::thread own?

queue v1

Queue v1 · Thread lifetime

1–2 · Problem

We want the producer and the consumer on their own threads. A std::thread is an object that owns a running OS thread. Before that object dies, somebody has to decide what happens to the thread.

In our project: Run producer(queue, N) on a new thread, then consumer(queue, N) on another. Passing the queue and finishing the threads correctly is the whole job.

2 · Mental model
std::thread object ──owns──▶ OS thread
  before it is destroyed, call one of:
    join()    wait here until it ends
    detach()  let it run with no owner
  destroyed while joinable → std::terminate

arguments are COPIED into the new thread
  std::ref(x) passes a real reference
3–5 · Tiny example

The thread that killed main. Predict:

  • What prints? Does the program exit normally?
  • Fix it. Now make main NOT wait for work().

Then break it:

  • detach() a thread inside a helper function that captures a local by reference. Keep main alive 3 s.
  • Pass a variable to a function taking int& without std::ref. Read the compile error.
6–7 · Explain + fix

Every thread needs exactly one owner that joins it. Join every thread, through an owner that can't forget. In this project we never detach.

8 · Project version
  • std::ref(queue): otherwise the thread gets a copy, or it doesn't compile.
  • ThreadGroup joins in its destructor, so an exception between starting and joining can't terminate the program.
  • The producer finishes before the consumer starts. Still no overlap.

Must pass:

  • Producer, then consumer, 1,000,000 items: size() is 0
  • Throw between add() and the end of scope: no terminate
Bridge

The test marked should fail: 4 producers at once, N = 100,000 each. That failure is the next topic's problem.

9 · Exercises
  1. Write ThreadGroup yourself, with deleted copy operations. Prove it joins when an exception is thrown.
  2. Rewrite v1 with std::jthread. What disappears from the code?
  3. Find the bug: char buf[64] passed to a thread function taking const std::string&, then the caller returns.
10 · Checkpoint answers
  1. What happens if a joinable std::thread is destroyed?
    std::terminate, immediately.
  2. Why does std::thread copy its arguments?
    The new thread may outlive the caller's stack frame. Copying is the safe default.
  3. Why is std::thread move-only?
    One OS thread must be joined exactly once; two handles would mean two joins.
  4. When is detach() safe?
    When the thread only uses data it owns (captured by value) or data that lives for the whole program.

EXERCISE 3 (classic Chapter 2 bug): the char buffer is converted to std::string inside the new thread, possibly after the caller's buffer is gone. Fix: convert first, std::thread t(f, std::string(buf)).

v2

Why do four producers crash the queue?

queue v2

Queue v2 · Races and mutexes

1–2 · Problem

Four producers pushing 100,000 items each crashed or hung on every run. With 1,000 each it always looked fine. Something inside push() can't survive two threads at once. We need to see exactly what, on something smaller than a std::queue.

In our project: Queue v1's push() is called from 4 threads at the same time. Nothing stops two of them from being inside it together.

2 · Mental model
++x is three steps:   read → add → write

T1 read 0
          T2 read 0
T1 write 1
          T2 write 1        one update lost

data race = same object, ≥ 1 write,
            no synchronization  → UB
mutex = only one thread inside at a time
3–5 · Tiny example

The counter that can't count. Predict:

  • What should it print? Run it 10 times at -O0 and write down every result.
  • Why isn't it always 2,000,000?

Then break it:

  • Build at -O2. Does the bug disappear? Is the program correct now?
  • Declare the mutex inside increment(). Does it still protect anything?
6–7 · Explain + fix

A mutex makes read-add-write happen one thread at a time. Protect data, not code: every access to shared data goes through the same mutex.

8 · Project version
  • Every access to q happens while holding m. That's the contract. Write "guarded by m" next to the member.
  • pop() throws on empty instead of undefined behaviour. That's honest, and the next version shows it's also dangerous.

Must pass:

  • 4 producers × 100,000: size() is 400,000, 10 runs out of 10
  • Time 1,000,000 pushes on 1 thread and on 4. Compare with v0
Bridge

The test marked should fail: One consumer starts first and retries on "empty". That failure is the next topic's problem.

9 · Exercises
  1. Time 4 counter versions at -O2: no lock, lock per increment, lock around the loop, local sum + one locked add. Explain the ranking.
  2. In your own words: why does an unsynchronized std::queue::push corrupt memory? (Hint: the deque's internal pointers.)
  3. Run the counter under ThreadSanitizer (WSL/Linux) on a run that happens to print 2,000,000.
10 · Checkpoint answers
  1. Race condition vs data race: what's the difference?
    Race condition: the outcome depends on timing (a logic problem). Data race: unsynchronized access to the same memory with at least one write (undefined behaviour in C++).
  2. Is flag = true in one thread, while another thread reads flag, safe?
    No. It's still a data race, even though it "looks atomic".
  3. What exactly does m protect?
    q, the data. Not the push function.
  4. Two threads push_back into two different vectors. Data race?
    No: different objects. The standard library only promises that concurrent const access to one container is safe, and that different containers are independent.

EXERCISE 1 RANKING: local sum fastest and correct; around the loop correct but serial; per increment correct and slow; no lock wrong.

v3

An exception left the queue locked forever

queue v3

Queue v3 · RAII locks

1–2 · Problem

pop() threw "empty" while holding the mutex. unlock() never ran, and every thread froze. We already solved this shape of problem once: ThreadGroup joins in its destructor, so exceptions can't skip it.

In our project: Queue v2 uses m.lock() and m.unlock() by hand. Any exception, early return or forgotten unlock between them leaves the queue locked.

2 · Mental model
object lifetime
   constructor   → acquire (lock)
   ...work...      may return early or throw
   scope ends    → destructor → release (unlock)

exception thrown
   → stack unwinds
   → destructors of every local still run

This is RAII: resource acquisition is initialization. Same idea as ThreadGroup in v1.

3–5 · Tiny example

The lock that never unlocks. Predict:

  • Does it print 1 (got the lock) or 0?
  • Fix it using only the object model. No try/catch.

Then break it:

  • Change try_lock() to lock(). What happens?
  • Write std::lock_guard<std::mutex>(m); with no variable name. Is the counter race back?
6–7 · Explain + fix

Constructor locks. Destructor unlocks.. Never call lock() and unlock() by hand. Let a destructor release the lock.

8 · Project version
  • lock_guard in every member function. No naked lock()/unlock() anywhere.
  • pop() still throws on empty, but now the throw releases the lock.

Must pass:

  • Consumer starts first, catches "empty", retries: no freeze
  • 4 producers × 100,000 still gives 400,000
Bridge

The test marked should fail: 2 consumers check empty() before pop(). That failure is the next topic's problem.

9 · Exercises
  1. Write your own LockGuard class with deleted copy operations, and use it in the queue.
  2. Use std::unique_lock to unlock early in a function that does slow logging after the critical section.
  3. Explain the bug in std::lock_guard<std::mutex>(m); in two sentences.
10 · Checkpoint answers
  1. Why lock_guard instead of lock()/unlock()?
    A destructor runs on every exit path (return, exception, break). Manual unlock can be skipped.
  2. What happens to local objects when an exception unwinds the stack?
    Their destructors run, in reverse order of construction.
  3. When would you pick unique_lock over lock_guard?
    When you need to unlock before the scope ends, defer locking, move the lock, or pass it to condition_variable::wait.
  4. What's the difference between lock_guard and scoped_lock?
    lock_guard locks exactly one mutex. scoped_lock (C++17) can lock several at once without deadlocking, and works with one too.
v3

Every call locks. Why does it still throw?

queue v3

Queue v3 · Interface races

1–2 · Problem

Consumers now check empty() before calling pop(). Both functions lock correctly. With two consumers and one item left, pop() still throws "empty". There is no data race. Something else is wrong.

In our project: Queue v3 offers empty() and pop() as separate calls. Each one is safe on its own. The consumer's "check, then take" is two calls.

2 · Mental model
if (!q.empty())     ← lock, check, unlock
                      ... another thread runs ...
    x = q.pop();    ← lock, pop, unlock

two calls = two lock acquisitions = a gap
check-then-act across a gap = race condition

This is a race condition with no data race. ThreadSanitizer stays silent.

3–5 · Tiny example

Every call is safe. The program isn't.. Predict:

  • The stack holds one element. Find an interleaving where top() runs on an empty stack.
  • Is there a data race here?

Then break it:

  • Add sleep_for(1ms) between empty() and top() to make it fail reliably.
  • Find the second bug: both threads read the same top(), then both pop.
6–7 · Explain + fix

The race is in the interface, not the code. Design concurrent APIs around whole operations. A check and the act it guards must happen under one lock.

8 · Project version
  • try_pop() never throws. It returns false when there's nothing to take.
  • empty() needs mutable std::mutex: locking changes the mutex, not the queue's value.
  • empty() only means "was empty a moment ago". Document it.

Must pass:

  • 2 consumers, slow producers: no exceptions, every item consumed once
Bridge

The test marked should fail: Idle consumers looping on try_pop() stay near 0% CPU. That failure is the next topic's problem.

9 · Exercises
  1. A thread-safe map has locked contains() and insert(). Write the race, then design insert_if_absent().
  2. Write three versions of try_pop: bool + out-parameter, std::optional, std::shared_ptr. List one pro and con of each.
  3. Find a check-then-act bug in one of your own past projects.
10 · Checkpoint answers
  1. Can a program have a race condition without a data race? Example?
    Yes. Every call locks, but empty()-then-pop() as two calls races. Also: a bank balance check followed by a separate withdraw.
  2. Why does std::queue::pop() return void?
    Exception safety: if returning the value by copy threw after the element was removed, the element would be lost.
  3. What does empty() promise in a concurrent queue?
    Only that it was empty at some moment during the call. By the time you act on it, it may be wrong.
  4. Why must empty() use a mutable mutex?
    empty() is const, locking modifies the mutex, and the mutex isn't part of the queue's logical state.
v4

try_pop returned false. Now what?

queue v4

Queue v4 · Waiting

1–2 · Problem

A consumer with nothing to do has three bad options: spin (burns a core), nap in a loop (adds latency), or wait inside the locked queue (freezes the producer out). What we want: release the lock, sleep using no CPU, wake when a producer pushes, then re-take the lock and check again.

In our project: Queue v3 can tell a consumer "nothing yet". It can't let a consumer sleep until something arrives.

2 · Mental model
consumer                      producer
lock m
queue empty → cv.wait(lock)
  (releases m, sleeps)
                              lock m, push, unlock
                              cv.notify_one()
wakes, re-locks m
re-checks: not empty → pop

The condition lives in your data (the queue). The condition_variable only says "go look again".

3–5 · Tiny example

Three ways to wait. Predict:

  • Option 1: what does CPU usage look like with an empty queue?
  • Option 3: run it with a producer. Why does everything stop?

Then break it:

  • Option 2 with a 1 µs nap, then a 1 s nap. Is there a good number?
  • Draw the wait-for graph for Option 3: who holds what, who waits for what.
6–7 · Explain + fix

wait() releases the lock and sleeps in one step. Waiting = a mutex + a condition in your data + a condition_variable. Always wait with a predicate.

8 · Project version
  • Three operations, three recipes. push: lock → push → unlock → notify. try_pop: lock → maybe pop. wait_and_pop: lock → wait for not-empty → pop.
  • try_pop stays: a consumer with other work shouldn't block.

Must pass:

  • Consumers start first and sit at ~0% CPU until items arrive
  • 1 producer, 1 consumer, 1,000,000 items: count and sum match
Bridge

The test marked should fail: Remove the predicate, start the producer first. That failure is the next topic's problem.

9 · Exercises
  1. Wait-for graphs: draw A→B vs A→B, A→B vs B→A, "wait for a flag while holding A", and "join while holding A". Which can deadlock?
  2. Add wait_and_pop_for(timeout) using cv.wait_for. What does it return on timeout?
  3. Stretch: a bounded queue. push() waits while full, using a second condition variable.
10 · Checkpoint answers
  1. Why does cv.wait take unique_lock, not lock_guard?
    wait() has to unlock the mutex while sleeping and re-lock it before returning. lock_guard can't be unlocked.
  2. Name the two problems the predicate solves.
    Spurious wake-ups and lost wake-ups (a notify before the wait).
  3. What can go wrong if push() changes q without the lock, then notifies?
    A data race on q, and the push+notify can land between the consumer's check and its sleep, so the consumer misses it and sleeps forever.
  4. notify_one or notify_all after one push? Why?
    notify_one: one item can satisfy one consumer. notify_all is for "everyone must react" (shutdown, v6).

EXERCISE 1: never / sometimes / always (if T1 locks first) / always (if T1 locks first). Waiting for a flag or a thread while holding a lock someone needs is also a deadlock.

Does it stay correct with 4 × 4 threads?

Queue v5 · Correctness under load

1–2 · Problem

One producer and one consumer work. Real systems have many of each, millions of items, and producers or consumers that are sometimes slow. One run that prints the right number proves nothing. We need tests a bug can't hide from.

In our project: Queue v4 under every workload we can think of, with checks that catch lost items, duplicates, hangs and wasted CPU.

2 · Mental model
4 threads, 1 mutex  (contention)
  T1 ██ lock ██ ........ ██ lock ██
  T2 ... waiting ... ██ lock ██ ....
  T3 ...... waiting ...... ██ lock ██
  T4 ......... waiting ..........

correct = count matches · sum matches ·
          each item once · no hang · no spin

Share less: contention, not locking, is the real cost. Concurrent code is verified by stress tests across workloads, never by one run.

10 · Checkpoint answers
  1. Why check the sum as well as the count?
    A duplicate and a loss can cancel out in the count; the sum (with distinct values) catches it.
  2. Why did 1,000 items per producer hide the v1 crash?
    Each thread finished before the next one started, so they never overlapped.
  3. What is contention, and why does it make 4 threads slower than 1?
    Several threads competing for one lock. They serialize, and passing the lock between cores costs more than the work itself.
  4. Why is "consumers know n" a design smell?
    Real producers don't announce how much they'll produce; consumers need to run until told to stop. That's a lifecycle, v6.
v5

Two queues, two locks: why did it freeze?

queue v5

Queue v5 · Deadlock

1–2 · Problem

With many consumers, one queue can pile up while another runs dry. We add move_all_to(other) to rebalance work. That needs two locks at once. Two threads moving in opposite directions froze 3 runs out of 3.

In our project: q1.move_all_to(q2) and q2.move_all_to(q1) run in loops on two threads. Each call locks its own queue, then the other one.

2 · Mental model
T1 holds q1.m ──waits for──▶ q2.m
T2 holds q2.m ──waits for──▶ q1.m

cycle in the wait-for graph = deadlock
break the cycle:
  · lock both at once      (scoped_lock)
  · or always in one order (e.g. by address)
3–5 · Tiny example

Manufacture a deadlock. Predict:

  • Run t1 and t2 on two threads. What happens?
  • Fix it without removing either mutex.

Then break it:

  • Remove the sleeps and run 20 times. Why is this version more dangerous in production?
  • Write push_all(batch) that locks m, then calls push() for each item. What happens?
6–7 · Explain + fix

Each thread holds what the other needs. Take several locks together, or always in one global order. And never lock the same mutex twice.

8 · Project version
  • scoped_lock for the two-queue operation, plus a self-move check (locking one mutex twice is UB).
  • push_all() takes the lock once and calls the private push_locked(), never push(). Public functions lock; helpers assume. No recursive_mutex.

Must pass:

  • Opposite-direction move_all_to loops, 100,000 each: no hang
  • q.move_all_to(q) returns immediately
  • push_all of 1,000-item batches: re-measure against single pushes
9 · Exercises
  1. Make push_all call push(). Watch it hang. Swap in std::recursive_mutex. Write one paragraph: ship it or not?
  2. Implement "lock the queue with the lower address first" using std::less<Queue*>. Compare it with scoped_lock.
  3. Stretch: Chapter 3's hierarchical_mutex, which throws when locks are taken out of order.
10 · Checkpoint answers
  1. What has to be true for a deadlock to happen?
    A cycle of threads each holding something and waiting for something another holds. (Formally: mutual exclusion, hold-and-wait, no preemption, circular wait.)
  2. Name two ways to make a two-lock operation deadlock-free.
    Acquire all locks at once (scoped_lock / std::lock), or acquire in one global order.
  3. Why check this == &other before scoped_lock?
    Locking the same mutex twice is undefined behaviour, even inside scoped_lock.
  4. Why is needing recursive_mutex usually a design smell?
    It usually means a public function calls another public function under the lock, so the lock boundaries don't match the operations, and the inner call can run with the invariant half-updated.
v6

The producers are done. The program never exits.

queue v6

Queue v6 · Shutdown

1–2 · Problem

Consumers no longer know how many items to expect, so they loop forever in wait_and_pop(). When the producers finish, every consumer sleeps forever, and ThreadGroup waits forever to join them.

In our project: Queue v5 has no way to say "no more items are coming". It needs states, and a way to tell every waiting thread about them.

2 · Mental model
RUNNING   push ok · pop waits
   ↓ shutdown()
CLOSED    push rejected · all waiters woken
   ↓ queue empties
DRAINED   wait_and_pop() → nothing
   ↓
consumers return · ThreadGroup joins them

Shutdown is a protocol: change the state under the lock, wake everyone, let each waiter see the new state.

3–5 · Tiny example

One flag, two waiters. Predict:

  • How many times does "woke up" print? Does the program exit?
  • What one-word change fixes it?

Then break it:

  • Set ready = true without the lock. What can go wrong?
  • Call notify_all() before starting the threads. Do they still wake?
6–7 · Explain + fix

Everyone who waits must be told: notify_all. A shared object needs a way to stop, and every waiting thread must find out.

8 · Project version
  • closed flag + notify_all. The predicate checks both conditions.
  • std::optional says "nothing more is coming", which no int can say.
  • Items already queued are still consumed (drain policy).

Must pass:

  • shutdown() with 4 sleeping consumers: all return within 100 ms
  • shutdown() with 1,000 queued items: all 1,000 consumed first
  • push() after shutdown() returns false
9 · Exercises
  1. Implement the other policy, "drop": shutdown() discards queued items. When would you want it?
  2. Bounded queue + shutdown: producers waiting for space must also wake up and give up. Implement it.
  3. Find the bug: shutdown() uses notify_one. Write the test that catches it.
10 · Checkpoint answers
  1. Why notify_all in shutdown()?
    Every sleeping consumer has to wake up and leave; notify_one wakes only one.
  2. Why does wait_and_pop() return std::optional<int>?
    A woken consumer needs a way to hear "nothing more is coming". No int value can mean that.
  3. What happens to items still in the queue at shutdown?
    With our drain policy they're still consumed; wait_and_pop returns nullopt only when closed AND empty.
  4. Why must closed be set while holding the lock?
    Otherwise it's a data race, and the write can slip between a consumer's check and its sleep (lost wake-up).

1–2 · Problem

2 · Mental model

    T v = q.front();    copy throws? item still
                        in the queue        ✓

}
caller: x = s.pop();    assignment throws? item
                        already removed     ✗

  1. Why move out of front() instead of copying?
    Copying may be impossible (unique_ptr) or may throw; moving is cheap and, for standard types, doesn't throw.
  2. Why does std::queue::pop() return void?
    So that a throwing copy of the returned value can't lose an element that's already been removed.

    Reverse order of declaration.
